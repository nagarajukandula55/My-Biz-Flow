# MBF Live Readiness Goal

**Status:** In progress; production acceptance gates remain open  
**Scope:** 24 registered MBF modules. Excluded by owner request: Service Centre, Restaurant POS, and Hotel. Static catalog checks may still read the complete 27-module registry, but this goal does not audit or change those three modules.

**Later scoped exception (28 November):** The owner specifically requested fixes to Service Centre alternate contact visibility and inquiry cancellation/sales-invoice conversion. Those files are changed for that request; the broader Service Centre audit remains outside this 24-module goal.

## Goal

Verify and close the implementation, security, workflow, UI, offline behavior, integrations, data handling, and operational gaps for every in-scope module so the product can be considered for production use. Do not declare live readiness from static route coverage or unit tests alone.

## Acceptance gates

1. **Module workflow review:** For every in-scope module, enumerate its user roles, entry points, create/read/update/delete actions, status transitions, validation and failure cases, documents/exports, reports, permissions, and cross-module dependencies.
2. **Tenant and authorization safety:** Verify every read/write is partner-scoped, every role-specific action is enforced on the server, and disabled modules/features deny access without unintended writes.
3. **Data correctness:** Verify currency units, tax/numbering behavior, stock and ledger effects, idempotency, transaction boundaries, reversals/refunds, and safe handling of historical records. No destructive migration or production-data mutation as part of this audit.
4. **UI and device use:** Verify routes, forms, empty/loading/error states, accessibility basics, responsive desktop/tablet/mobile layouts, offline drafts/queues, and clear user guidance.
5. **Integrations and notifications:** Verify configured provider behavior, success/failure/retry handling, webhook authentication/idempotency, and Telegram/email/SMS/WhatsApp events that are enabled for each module.
6. **Automated checks:** Typecheck, lint, relevant unit/safety tests, disposable-database integration tests, and production build must pass. Failures must be fixed or explicitly classified with owner and blocking effect.
7. **Production acceptance:** Verify required production environment variables, database connectivity/migrations, scheduled jobs, external provider credentials/webhooks, and representative end-to-end smoke scenarios against an approved non-customer test account. Do not claim this gate from local checks.
8. **Release handoff:** Summarize per-module status, unresolved blockers and evidence; provide deployment and push commands only after the code and release gates are reviewable. Do not push or deploy as part of this goal without explicit instruction.
